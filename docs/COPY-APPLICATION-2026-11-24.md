## Technical copy standards

Every technical description should identify the problem and intended user, architecture and system boundary, hardware target and compatibility assumptions, dependencies/source revisions/licences, implementation state, test method and result, security/privacy boundary, backup/restore/rollback, limitations and maturity.

Use precise labels: **DOCUMENTED, CONFIGURED, BUILT, TESTED, VALIDATED, DEPLOYED, PRODUCTION-VERIFIED, RESEARCH, EXPERIMENTAL, PLANNED, BLOCKED, UNKNOWN**. A successful build is not deployment. A technology inventory is not an installed system. A research direction is not a customer offer.

## Design copy

Use editorial technical language: clear labels, diagrams with explicit boundaries, readable code and monospace metadata. Avoid generic AI visuals, neon dashboards, unexplained acronyms and claims such as “military-grade”, “unbreakable”, “fully secure” or “production-ready” without evidence.

The shared visual system uses near-black, ivory, forest green, sage, ochre/gold and terracotta. Use the palette to support hierarchy, not as decoration.

## Customer and transaction boundary

Potential customer engagements are scoped and transacted through NAKEBUSEN. Public copy may describe candidate capability areas but must not promise immediate availability, fixed prices, certifications, uptime, security guarantees or customer outcomes without current evidence.
