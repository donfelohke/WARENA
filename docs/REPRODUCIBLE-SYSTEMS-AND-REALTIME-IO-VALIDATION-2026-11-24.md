# WARENA — Reproducible Systems and Real-Time I/O Validation

**Date:** 2026-11-24  
**Status:** RESEARCH / PROPOSED VALIDATION PROTOCOL  
**Scope:** Guix-based system reproducibility, software provenance, native media pipelines and sustained camera-to-display workloads.  
**Relationship:** Supplements the existing [Camera, Display and Real-Time I/O at Scale study](CAMERA-DISPLAY-REALTIME-IO-SCALE-RESEARCH-2026-11-24.md). It does not replace that architecture study or claim a completed benchmark.

## 1. Decisions this research should support

1. Can a WARENA host be reconstructed from pinned source and channel revisions?
2. Can an artefact's origin, build process, dependencies and integrity be inspected?
3. Which native Linux media path is best for a specified camera/display workload?
4. What are the actual throughput, latency, memory, power and thermal limits on the target hardware?
5. Can the system remain useful under interrupted connectivity, constrained power and replaceable hardware?

No workstation is assumed to be present or qualified. A proposed HP EliteBook 835 G8 / Ryzen 5 PRO 5650U class host is a candidate test target only; record the actual machine identity and configuration before benchmarking.

## 2. Guix reproducibility: minimum evidence set

The GNU Guix Reference Manual documents `guix describe` as a way to identify the Guix revision and channels in use. Its channel documentation describes saving pinned channel commits and reusing them with `guix pull -C` or `guix time-machine -C`.

A minimum reproducibility record should contain:

- `channels.scm` generated by `guix describe -f channels`;
- `manifest.scm` for the exact user-space environment;
- system configuration and Guix Home configuration, where applicable;
- Guix and channel commit IDs, package derivations and relevant package definitions;
- target architecture, kernel, firmware, bootloader, drivers and hardware inventory;
- build command, environment variables, locale, time source and build logs;
- hashes of outputs and the independent rebuild result;
- documented exceptions: firmware, hardware-specific blobs, network-fetched inputs, mutable state and non-reproducible upstream packages.

Illustrative capture commands (not yet run on a WARENA host):

```sh
guix describe -f channels > channels.scm
guix package --export-manifest > manifest.scm
guix describe
```

A later reconstruction should use the saved channel file, not an unpinned current channel:

```sh
guix time-machine -C channels.scm -- shell -m manifest.scm -- <command>
```

The exact command and manifest syntax must be checked against the Guix version being tested. A reproducible user-space environment does not by itself reproduce firmware, device state, external services, mutable user data or a complete bootable host.

**Acceptance evidence:** a second clean environment reconstructs the pinned package environment; the report records any output differences, unavailable substitutes, unsupported hardware and non-reproducible components. Do not call a build reproducible solely because it succeeded twice on the same machine.

## 3. Software supply-chain evidence

Map actual repository and release practices to these references:

- [NIST SP 800-218 SSDF 1.1](https://csrc.nist.gov/pubs/sp/800/218/final): secure development practices, source review, dependency management, release protection and vulnerability response.
- [SLSA v1.2](https://slsa.dev/spec/v1.2/): build provenance and source/build integrity. A CI workflow alone does not establish a SLSA level.
- [SLSA Build Provenance](https://slsa.dev/spec/v1.2/build-provenance): record the builder, build definition, resolved dependencies and produced artefacts.
- [SPDX](https://spdx.dev/specifications/): machine-readable component and licence metadata. An SBOM does not prove a complete licence or vulnerability audit.
- [Reproducible Builds](https://reproducible-builds.org/docs/): independent rebuilds and comparison of output artefacts.

For each release candidate, retain source revision, build definition, builder identity, dependency resolution, SBOM, signatures/attestations where available, hashes and verification instructions. State which controls are implemented, partially implemented, absent or not assessed. Do not claim ISO/IEC 27001 certification or SLSA conformance without the relevant assessment and evidence.

## 4. Native media stack qualification

The existing camera/display study correctly treats V4L2, Media Controller, libcamera, DMA-BUF, PipeWire, GStreamer and DRM/KMS as separate interfaces. This protocol turns that map into a comparative experiment.

For one identified hardware target, compare only paths the actual devices support:

| Candidate path | Test question | Required evidence |
|---|---|---|
| Direct V4L2 | Does the device expose stable formats, controls and timestamps? | `v4l2-ctl --all`, format/queue details, driver/kernel version, sample logs |
| libcamera | Does a maintained pipeline handler support the sensor/ISP and required controls? | `cam -l`, camera configuration, request completion, metadata and build provenance |
| GStreamer | Can the pipeline negotiate timestamps, clocking, bounded latency and sink presentation? | Pipeline description, latency query, clock source, queue limits, dropped-buffer counters |
| PipeWire | Is graph routing needed, and what latency/quantum does it introduce? | Node graph, negotiated formats, quantum, scheduling and xrun/drop evidence |
| DRM/KMS | Which planes, formats and atomic commits are actually supported? | Connector/plane inventory, atomic test result, mode and presentation measurements |
| DMA-BUF | Is sharing genuinely copy-free end-to-end? | Exporter/importer, format/modifier, fence/sync behaviour, CPU/GPU mapping and measured memory traffic |

Do not assume a zero-copy path from a DMA-BUF file descriptor or assume that combining every framework improves the system. Start with the least complex viable path and add components only when a measured requirement demands them.

## 5. Benchmark protocol

### 5.1 Test identity

Every run records:

- host make/model and exact CPU, RAM, GPU, storage and display;
- firmware/BIOS, kernel, driver, Guix revision and package/channel commits;
- camera model, sensor mode, lens, exposure, pixel format, resolution and frame interval;
- display model, mode, refresh rate, plane/composition path and brightness;
- room temperature, ambient light, power source and thermal state;
- source revision, configuration, workload, command and raw log location.

### 5.2 Workloads

Run separately: idle display; camera capture only; capture plus display; capture plus one processing stage; multi-stream capture; sustained recording (only if required); hot-plug/restart; and offline operation. Use synthetic or test-chart inputs before any participant imagery.

### 5.3 Metrics

Report sample count and distributions, not only averages:

- capture frame interval and achieved frame rate;
- capture-to-buffer, buffer-to-processing, processing-to-submit and submit-to-photon latency;
- glass-to-glass latency with an explicitly documented measurement method;
- p50, p95, p99, maximum, jitter definition and deadline misses;
- dropped/repeated frames, queue depth and time spent at each queue;
- CPU/GPU utilisation, memory use and memory bandwidth where measurable;
- power draw at idle and under sustained load, energy per operating hour;
- component temperatures, fan behaviour and throttling;
- recovery time after device loss, process failure and power interruption.

A high frame rate does not prove low latency. A mean does not describe tail behaviour. Timestamp subtraction is invalid unless clock domains and conversions are documented. If no photodiode/high-speed measurement or validated equivalent is available, mark submit-to-photon as NOT MEASURED.

### 5.4 Repeatability

Use a fixed workload and configuration; warm up consistently; perform at least three independent runs for exploratory comparison; publish raw results and outliers; record measurement uncertainty and instrument calibration. Three runs are an initial engineering screen, not a universal statistical sufficiency claim. Increase repetitions when variance or the decision's consequence requires it.

## 6. Kenya / East Africa operating conditions

Translate local constraints into measured design inputs rather than generic assumptions:

- **Connectivity:** test install, documentation and ordinary operation offline; measure download size and recovery after network loss. CA's national prepaid/mobile statistics justify evaluating low-data operation but do not establish an individual site's connectivity.
- **Power:** measure actual host and display watts, startup surge where relevant, energy per hour and safe shutdown behaviour. Use the relevant EPRA tariff and local outage records before specifying UPS or solar capacity.
- **Repairability:** record replaceable parts, local supplier availability, lead time, connector standards, tools and technician requirements.
- **Cost:** distinguish purchase cost, energy, storage, consumables, replacement and support costs over an explicitly stated period.
- **Language and accessibility:** test readable interface text, keyboard/control alternatives and documentation with intended users; do not treat English-only success as universal usability.
- **Data governance:** keep participant media out of routine performance logs; use synthetic targets; if human capture is necessary, document lawful basis, consent, retention, access and deletion before collection.

## 7. Quality model and release gate

Use [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html) as a quality-model reference, selecting characteristics that match the system: performance efficiency, reliability, security, compatibility, maintainability, flexibility and safety where applicable. Convert each into an explicit requirement and test. The model is not a certificate.

A release candidate is not qualified until the test record includes:
- defined use case and failure consequences;
- pinned environment and provenance;
- hardware and software configuration;
- raw measurements and reproducible analysis;
- limitations and failed tests;
- repair/recovery procedure;
- security and privacy review;
- an explicit owner decision.
